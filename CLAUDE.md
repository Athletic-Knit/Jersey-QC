## What the app does

A React/Vite web app for quality control of sports jerseys on the factory floor. The operator lays each jersey under a camera; Claude Haiku reads the name and number off the photo; the app matches the read against the order's roster and tells the operator what to do with the jersey. A small server ("the hub", inside the Vite server) collects every station's progress for the supervisor's board, keeps a 90-day ledger, drives the Zebra label printer and keeps unfinished orders.

How to use the screens, step by step, is in `docs/OPERATOR-GUIDE.md`. The rules behind them are below.

### Roles and sign-in

- Sign-in is a role, then (at a station) the station, with a PIN (`ROLES`, `STATIONS` in config.js). The PIN is checked by the server (phase 7 of the admin panel, 26 Nov 2026: `POST /api/admin/pin`, `src/lib/pins.js`, `checkPin` in hub.js); the page holds none of the PINs set in `.env.local` as `JQC_PIN_…` and hears yes or no (the defaults are in `pins.js`, which the page loads for a server without the admin plugin, and any `VITE_PIN_…` still reaches every browser; the admin panel's Floor rules warns about both). Each PIN comes from `.env.local`: `JQC_PIN_<ID>` first, then the old `VITE_PIN_<ID>`, then the default (inspector 1111, sorter 4444, packer 2222, supervisor 3333, stations 1001–1003), the same values as before. A `VITE_` name still reaches every browser (Vite hands `VITE_` variables to the page), so rename them to `JQC_PIN_…`. Ten wrong PINs in a row for one role or station from one PC lock that one for a minute (`PIN_TRIES`, `PIN_LOCK_MS`); a right PIN clears only its own count, so a PIN someone knows never resets the count for guessing another. A server with no admin plugin (`vite.config.diag.js`) has no route: only there the page checks the old names or the defaults itself. A server that cannot be reached is a no. `VITE_PIN_REQUIRED=false` switches the gate off.
- **Inspector** and **Sorter** sign in at a station (`?station=station1` … `station3`) with the station's PIN. Names come from `VITE_OPERATORS`; "Other" asks for the name on the screen's keys.
- A **Sorter** only sorts (the owner, 19 Nov 2026): no quick look, no full inspection, no double-check, no damage photo; the only flags are No size tag, Duplicate and Not on the roster. A sorter's unfinished orders are picked up by sorters only (`kind` on the entry).
- **Supervisor** gets the board and nothing else: no station behind it, no scanning, no resume; its header button is Sign out.
- **Packer** is shown but cannot sign in (`BLOCKED_ROLES`): the packer side is not built.
- **Admin** (the co-op, 27 Nov 2026) is the last choice on the sign-in screen (`ADMIN_CHOICE` in App.jsx, added to `ROLE_CHOICES`, not to `ROLES`): no station and no PIN. Already signed in to the panel (`GET /api/admin/session`): "Signed in as …" and "Open the admin panel →" to `?view=admin`. Not signed in: the panel's name and password right on the card ("Sign in to the admin panel →" posts the panel's own `/api/admin/login`, which sets its cookie, then opens it; `JQC_ADMIN_PASSWORD`, checked by the server, is the gate). A server with no admin plugin (`vite.config.diag.js`) or no password says so and greys the button. It is not a floor role.
- **The sign-in card keeps one shape** (the co-op, 27 Nov 2026): one width (940) and one body height (`SIGNIN_BODY_MIN`, the PIN and its keypad) whatever role is picked; the role row spans the card under the letterhead, five tiles in one row. Under it, the left column is the role's own (station and name; the name for the board; the panel's name for Admin) with Sign in at the bottom, level with the keypad's last row; the right is the PIN, or for Admin the panel's password. No line explains a role (the co-op, 27 Nov 2026); under the stations only the in-use warning.
- An operator's station goes full screen on sign-in. One browser per station: a station live from another PC (reported within 20 s, `LIVE_MS` in hub.js) is shown as in use; a signed-out station is free at once.

### An order at a station

1. **Start.** The operator picks a roster the supervisor sent ("📥 Assigned orders · N"), opens an unfinished one ("⏸ Unfinished orders · N"), or uploads a roster file, and fills the order number (digits only, on a keypad). Starting a sent roster takes it on the hub: one station per order; other stations see it greyed "In progress on Station 1" and get a 409 if they race. The jersey type is picked here or on the supervisor's send form: ECHL / ECHL replica (stitched) or Sublimated (printed) (`JERSEY_TYPES`), and so is the garment (hockey by default; see "Garments"). The setup form has no order-notes box (17 Nov 2026); notes come with the supervisor's roster. The order is sorted into boxes by team, by size or not at all (`BIN_BY`).
2. **Each start of an order is a run** (`orderRun`, the time it started; kept when another station picks the order up). The ledger keeps one order record per run, so an order started again by mistake does not overwrite the finished one.
3. **Set out the boxes** (below), then scan jersey by jersey: pedal, hands-free, or the SCAN button.
4. **The result screen** for each jersey: green, yellow or red (see "Matching").
5. **Finish order**, or **Finish later** (see "Finishing an order").

## Tech stack

- React 19, Vite 8 (ESM), Vitest 3 (jsdom and Testing Library for the App smoke tests). The servers are the Vite dev server in every stage, production included: there is no build step.
- `src/App.jsx` (~5,600 lines): every screen, all state in the top-level `App` component, no state library, inline styles, colours from the brand tokens in index.css (light by default). The rules live in `src/lib/*.js`, which have tests.
- `src/config.js`: floor configuration (keys, reasons, checks, jersey types, the garment menu, roles, PINs, default settings). `src/lib/garments.js`: the garment outlines and the catalogue's style table (see "Garments").
- `hub-plugin.js`: the hub (routes, ledger, printing). `replay-plugin.js`: the replay source, development and testing only. `admin-plugin.js`: the developers' admin panel's server side (see "The admin panel").
- Type and far-view scale: `src/index.css` ships three self-hosted typefaces (`@fontsource`): Barlow for UI text (`FONT_UI` in App.jsx), Atkinson Hyperlegible kept for player names and roster cells (`FONT_READ`: it keeps 0/O, 1/l/I and 6/9 apart when read from 4–5 ft), and Barlow Condensed for the big numerals (jersey number, size, box, the counters: `FONT_DISPLAY`) and the titles. The stations are 27" monitors read from 4–5 ft, so `#root` gets `zoom: 1.15` at ≥1600×800, `1.3` at ≥1600×1000 and `1.7` at ≥2300×1200, by the window each station really has (a 1080p screen in a browser window with the taskbar leaves ~945 px and gets 1.15; full screen or kiosk gets 1.3; the owner, 20 Nov 2026: some operators keep the taskbar, some do not). Everything is laid out in the smaller logical viewport and enlarged, so full-height boxes use `100%`, not `100vh`. Dialogs keep their title and buttons on screen and scroll only their list (`maxHeight` + a flexing list; a long dialog's head is sticky, `STICKY_HEAD`, the owner, 19 Nov 2026).
- Brand (27 Nov 2026): the Athletic Knit guide's palette is the colour tokens in `src/index.css`, light and dark (the short set and the `--k-*` set; screens use `var(...)`, no literal colours except black behind the camera, text on the camera video and the wall view's own dark palette; washes are `--k-tint-*`, dialog scrims `--k-scrim`). The logo is `src/assets/ak-logo.jpg` (colour on white: bare in light, on a white tile in dark, `.ak-logo`). Status pills are a dot and a word, never colour alone. Stations default to the light theme; one that chose Dark keeps it.
- SheetJS from CDN (`https://cdnjs.cloudflare.com/ajax/libs/xlsx/0.18.5/xlsx.full.min.js`) for Excel read and write; ExcelJS from CDN (`exceljs/4.4.0`) for the damage report with photos (`src/lib/damage.js`).
- The read: Claude Haiku 5.5 (`claude-haiku-5-5`), thinking off, low effort, an 800 px frame (`src/lib/vision.js`; overrides in the environment table; `claude-sonnet-5-5` reads the same cases at ~1.9 s). The page calls `/api/anthropic/v1/messages`; the server's AI proxy (`ai-proxy.js`, on every stage since phase 6 of the admin panel, 26 Nov 2026) forwards it to `https://api.anthropic.com` and adds the API key, so the page never holds it. It passes only the app's own reads with the server's key: POST `/v1/messages`, a model on the allowed list (`ALLOWED_MODELS`: Haiku 5.5 and Sonnet 5.5, plus `VITE_CLAUDE_MODEL` and the panel's model), at most 2 MB and `max_tokens` 4000 (what `vision.js` asks with thinking on) and 4 messages, not streamed, at most 120 reads a minute from one address and 600 from all; anything else gets an Anthropic-shaped error (403, 400, 413, 429, 404) the station shows. The call to Anthropic is stopped after 30 s (`UPSTREAM_MS`, the station hears 504) or as soon as the station hangs up, so a slow answer is never paid for twice; a client's `anthropic-beta` header is passed only with its own key. A request that brings its own `x-api-key` (the test tools) spends its own key and is neither checked nor counted, and is taken from the server's own PC only, or from any PC on development and testing (`ownKeyFromAnyPc` in `vite.config.stage.js`). The station's name for the counts is the `x-jqc-station` header only when it looks like `st-…` (`stationName`), else the PC's address; the counts never fail a read and a damaged counts file is cleaned on load (Fable's review of phases 5-8). Every read with the server's key is counted per day, station (the `x-jqc-station` header the station sends) and model: calls, failures, refusals, time (in 250 ms buckets), input, output and cache tokens; kept in `data/<hub data file>-ai.json` (written at most once a minute, 60 days, never served). One log line per call (status, time, address, station). The old `anthropicProxy` in vite.config.js is kept only for `vite.config.diag.js`.
- HTTPS everywhere (`@vitejs/plugin-basic-ssl`, a self-signed certificate): browsers allow the camera only on a secure origin. An address typed with `http://` to the HTTPS port is redirected (`redirectPlainHttp`).

## Roster file format

Files: `.csv`, `.tsv`, `.txt`, `.xlsx`, `.xls` (`parseCSV`, `parseExcel`, `rowsToRoster` in `src/lib/roster.js`).

- **The header row** is the first of the first 15 rows that names the players (a name or number column), or, for a blanks order, a size column with a quantity or team column. Title rows above it are skipped. Excel: the first sheet that has a header row. CSV: comma, tab or semicolon, whichever the first lines use most. A byte-order mark is ignored.
- **Columns** (case-insensitive; every other column is kept and shown):

| Field | Headers accepted |
|---|---|
| `name` | name, player, player name, playername, last name, lastname, surname, last, full name, fullname |
| `number` | number, no, no., #, num, jersey, jersey #, jersey#, jersey number, jerseynumber, jersey no, jersey no., shirt number, shirt |
| `team` | team, team name, teamname, club, squad |
| `size` | size |
| `size range` | size range, sizerange, range, age group, agegroup. Merged with `size` into `A-L`, `Y-M` (either half blank: the other alone). |
| `order` | order, order number, order no, order no., order #, order#, ordernumber, order id, po, po number, po #, po#, job, job number, work order, wo. Fills the order number; not kept as a column. |
| `quantity` | quantity, qty, qty., count, pieces, pcs, units, how many. That many rows (at most `MAX_QUANTITY` = 1000 a line, `MAX_ROSTER` = 5000 in all); not kept as a column. |
| `style` | style, style number, style no, style no., style #, style#, sku. Kept as a column. |
| ship with | any header starting "ship with", "ships with", "shipping with" or "ship w/" (see "Orders that ship together"). |
| colour | colour, color, colourway, colorway, jersey colour, jersey color, body (`colour.js`). Used to tell twins apart; optional. |

- **Rules for the values:**
  - `name`: **exactly as printed on the jersey** (Noam, 23 Nov 2026). Matching rules under "Matching".
  - `number`: **exactly as printed**: 07 and 7 are different jerseys, as 00 and 0 are (Noam, 23 Nov 2026; `normNum` keeps leading zeros). An Excel cell shown as "07" is read as "07" (`raw: false`). A number Excel formats with decimals, "12.0" or "7.00", is 12 or 7; "07.0" is 07 (code review, 23 Nov 2026).
  - `team`: optional, used for boxes. **Never read as a jersey colour** (Noam, 23 Nov 2026): a colour, if wanted, goes in a colour column.
- **Order number in a title row:** "Order 55555", "Order no: 55555", "PO# 55555", "Job …", "Work order …". The value needs a digit ("Order Form" is not order "Form"). With both, the first order number found wins (`orderNumberOf()`).
- **Ship with in a title row:** "Ship with 264248", "Ships with: 264248, 264249", "Ship w/ #264248 & 264249". Never taken for the order's own number (`shipWithOf()`, `orderList`: numbers of 3 digits or more; a run of 12, 18 … digits is split in sixes, as order numbers are six digits, the owner, 20 Nov 2026).
- **Quoted cells:** `"Smith, John"` is one cell, `""` is a quote. A line break inside a quoted cell is a space. A quote opens a quoted cell only at the start of a cell (a stray inch mark `12"` cannot swallow lines), and a record that takes in more than two line breaks falls back to plain lines (`splitCSVRecords`).
- **Two columns for one field:** the last one is the field, except that a duplicate that is empty, or (for the number) is not mostly 1–3 digit numbers or is a 1, 2, 3 … line count, is passed over and kept under its own header (Number + a Home/Away "Jersey" column; code review M17). The order column keeps its own rule: the first order number found.
- **The app's own export** re-used as a roster: its result columns (status, bin, box, reason, resolution, inspected by, time) are dropped, so yesterday's results do not come back as roster data.
- **Lines with no name and no number** are blank jerseys (no decoration). They are kept when the file has no name and no number column at all (and the line has a size, size range or team), or the line has a quantity; otherwise the line is dropped (`isBlankRow`, `blankGroups`).
- **Size order** (`sizeRank`, `bySize`): youth, then adult, then ladies (`L-M`, with the dash).
- **Short sizes** (the owner, 25 Nov 2026: "L-S, not Ladies-S"): `shortSize(size)` in roster.js writes "Ladies-S", "Ladies S", "ladies small" as L-S, "Youth M" as Y-M, "Adult 2XL" as A-2XL; a size already short, XL, OSFA and "" come back unchanged. It is applied where a size is drawn or printed (the roster table, the pick-list tiles, the green SIZE box, the Last passed strip, the Packing and board lists, the box label's size, the count label's mix, the list lines, the sticker, the ticket, the summary lines, the size filter) and nowhere else: matching, `sameSize`, the stored row, the Excel sheets and the hub keep the file's own spelling. The pick list's grey line says "L- sizes first" (`lastSizeLetter`).

## Matching: what a read becomes

The camera's read (`readJersey` in vision.js) goes to the matcher (`findMatches` in `src/lib/match.js`), and the matcher's answer decides the screen (`screenFor` in `src/lib/scanpolicy.js`, used by App.jsx and by the operator simulation alike). In order:

| The read | Screen |
|---|---|
| the API call failed | red **SCAN FAILED** |
| nothing readable: an empty table (`jersey_present` false) or no name and no number in view | no screen, nothing in the log. Hands-free learns the table and stays silent; a pedal press shows a yellow notice "No jersey in view" / "No name or number in view" for a moment. A read with any name or number is never "nothing", whatever `jersey_present` says. |
| no match could be made | red **COULD NOT READ** |
| one open row, sure | **GREEN** |
| the jersey's row is done already (passed, by hand, or flagged) | **ALREADY DONE** |
| rows to choose from, or near misses | **YELLOW** list |
| nothing on the roster like it | red **NOT FOUND** |

### When a read may be green

- **Green needs a name AND a number that both agree with one open row, read in full.** A number with no name read, on a roster that has names, is yellow (the name may be hidden, and so may a digit). A number-only row is green on a clean, complete, centred read of its number with no name on the jersey.
- **N1 (Noam, 23 Nov 2026): a doubtful read is ALWAYS yellow**, also when name and number match a row exactly, and also when the doubtful field came back empty. Doubtful = part of the name or number covered or cut off (`name_complete` / `number_complete` false), or a one-digit number off-centre or on a jersey not laid flat (`isDoubtfulRead`). Such a list is marked `doubtful` and stays a list even with one row.
- **N2 (Noam, 23 Nov 2026): 07 and 7 are different jerseys.** When #7 and #07 are both on the roster the camera's read is trusted, with no extra question (the owner, 23 Nov 2026). A read of 07 offers #7 as a near miss on the list, never as a match.
- **N4 (Noam, 23 Nov 2026): green needs the whole name.** Only capitals, accents and apostrophes may differ (O'NEIL = ONEIL, CÔTÉ = COTE), and spaces and hyphens are ignored (DE LA CRUZ = DELACRUZ; the owner, 23 Nov 2026). One word of a longer name, missing letters or extra words go yellow (`nameMatches` in text.js). Letters that do not decompose (ø, ł, ß) are dropped on both sides; the floor does not use them.
- **N5 (Noam, 23 Nov 2026): the team column never decides a green.** Colour comes only from a colour column. A row with no colour is "unknown", never ruled out.
- **The owner, 23 Nov 2026: a name read on a jersey whose row has no name is always yellow**, it may be a stray jersey from another order. **Except (the owner, 25 Nov 2026, 5h):** on a roster with no names at all the name the camera read is noise, so a clean (not doubtful, number complete) read of a number with exactly one OPEN row is green whatever name or team was read (`findMatchesInner`, the `numberOnly` check before the NN pick); two open rows of the number, a doubtful read and a typed entry are as before, and a roster with names keeps the rule. The owner accepts the risk that a stray garment from another order with that number goes green; invariant 8 allows the name only in that case. **One garment (the co-op, 25 Nov 2026):** on such a roster, when the open rows of the number read are all ONE size (and one colour, where a colour column says), they are the same garment made for different teams' players, so a clean camera read, or the number typed by hand, is green on the first open one in roster order and goes in that row's box (`oneGarment` in match.js, `sameGarment` on the answer): "it doesn't matter which one we select". Two sizes, a doubtful read (N1) and a roster with names stay a list. On a by-team order the garment goes in the first team's box; teams whose garments look different need a colour column. Rows with no size are not one garment: a list, as before (Fable's final review, 26 Nov 2026). A number read on a row with no number does not match it either.
- **A list with one jersey on it goes straight to the green** (the owner, 19 Nov 2026: "why bother with showing it"), but only on a clean, complete read (N1) and only when that row is what was read: its number digit for digit, its whole name, and a row with no name only when no name was read (`agreesWithRead`). Three kinds of list stay a list with one row: a doubtful one, one trimmed for the eye (`withoutNamed`, `trimmed`: the named rows still count), and the last open twin the colour seen argues against (`twins`).
- **Done rows leave the list** (9 Nov 2026); a list where every row is done is ALREADY DONE.
- **One digit read:** when it is on the roster, the list has the rows with that digit and nothing else (#4 lists the #4 rows, not #40 or #14; the owner, 19 Nov 2026). Hidden-digit numbers (`hiddenDigitNumbers`) are offered only when the read matches no row. The read prompt asks the model to report a hidden second digit only on evidence (a fold, crease, sleeve, hand, tag or picture edge beside the digit). A digit under a fold is a rescan.
- **Near misses** (`nearNumbers`): one look-alike digit off (6↔9, 1↔7, 3↔8, never 0↔4), a missing digit, a sleeve digit doubled ("88" for #8). A read longer than 2 digits (sleeve numbers merged, "777") offers its 1–2 digit parts (`subNumberCandidates`).
- **Turned jerseys:** the read returns `orientation`; when it is not `upright` the app turns the frame (`rotateDataUrl`) and reads again, and the two reads reconcile (`src/lib/vigilance.js`). A nameless 6/9, 18/81, 66/99, 60/09 on a turned jersey with the twin number open on the roster is a question (`rotated180`). Since 25 Nov 2026 (the owner) it is a question on every camera read, turned or not: a read number with a 180° twin, no name anchoring a row, and both numbers open on the roster lists both, the number read first (`twins`: a list of one stays a list; `twinOf`, set only when both numbers are on the list: the grey line "6 or 9? both are listed · #6 first", and `sortCandidates`' `after` keeps the twin's rows after the number read's; each number's part is the last confirmed size first, then every other size in rack order, whatever the station's sort and with no family step: read #6 after a Y-L, the list is #6 Y-L, the other #6 sizes, then every #9 the same way, the co-op, 25 Nov 2026); typed reads, self-twins (11, 69, 88) and a twin with no open row are as before. A turned jersey keeps its own path in `findMatchesInner` (it needs only the twin open, and its own wording); a turned 9 re-read upright as 6 settles on the upright read, which is itself that list (`settleTurned`). The invariants' `related` counts a 180° twin as related.
- **Self-check after a mistake** (`createVigilance` in vigilance.js): when the operator corrects the app (a green typed over, a list without the jersey, a "could not read" then typed, a pass un-checked) the next 5 jerseys are read twice and must agree before a green; another mistake restarts the 5. The header shows "Checking · N". The counter is saved in the session (`vigil`). Not for a sorter.
- **The amber line** "Camera could not see the whole number — check it is #N" (`numberDoubt` in ScanOverlay) shows on a green that still carries a camera read with `number_complete` false: since N1 that is the green after a pick from a doubtful list.

### Typed entries ("Enter by hand", key W)

- A typed entry is never doubtful: the operator's word stands.
- A typed number is the number: a one-row list goes straight to the green only when that row's number is the number typed (typed 400 is not #40, typed 122 is not #12; `typed-number.test.js`). A typed number does not match a row with no number (typed SAMUEL 9 is not the numberless Samuel).
- A typed name, when the row has one, must be the whole name: typed SMITH 12 where #12 is JONES is a question (code review, 23 Nov 2026). Choosing a team in the hand form never passes a row whose name differs from the name typed.
- A typed number on the roster (one row, or a row picked from the list that follows) goes to the same GREEN screen a scan gets: checklist, Confirm, Flag, and "← Back" to the form in place of Retry (the owner, 20 Nov 2026). Confirm records a plain pass with the note "Entered by hand", no supervisor sign-off (the owner, 20 Nov 2026).
- **A typed number on no row** gets a check step first: "#88 is not on the roster — check the number", with ← Back first (the pedal goes back to the form), then "#88 — not on the roster", then Flag (code review M18).
- The list after a number was typed: Back, "#N — not on the roster" and the same 🚩 Flag as the camera's list (the owner, 20 Nov 2026). Its flags take the TYPED number, name and team, not the camera's read (`flaggedAs`; `typed` is carried to the `listFlag` and `offSize` screens), and work with no camera scan behind them.
- A typed entry keeps what was typed: `typed` on the log entry ("Typed: #N · NAME") and on the hub event beside the camera's `read`.

## The station: screens and floor rules

### Keys and the pedal

- Defaults (`DEFAULT_SETTINGS` in config.js; changeable in Settings): scan **Enter**, select **Enter** (one pedal does both, the owner, 17 Nov 2026), highlight down **A** (or ↓), up ↑, retry **R**, Enter by hand **W**. The By hand key opens the form from the camera screen, like the ⌨ By hand button (which shows the key), whenever no result screen or dialog is up and no read is running (the co-op, 25 Nov 2026: it was read only by the result screens, which no longer offer By hand). The floor uses a foot pedal or a barcode scanner mapped to keys (voice commands were removed on 5 Nov 2026).
- A station's saved settings move once from `jerseyqc.settings.v2` to `v3` (`loadSettings` in persist.js): B becomes Enter, the stickers go off, everything else is kept.
- The scan key works only when no screen or dialog is open, and takes the focus off a button first (Enter on a focused button would click it). While the cursor is in a text box the scan key types, so Enter and Esc leave the box.
- **No scan behind a dialog** (code review H1, 23 Nov 2026; the floor's first rule: no jersey passed unseen). App.jsx has ONE list of every dialog (`dialogOverResult`; `anyDialogOpen` = that list plus Blanks). The pedal, hands-free, SCAN, By hand, `doTriggerScan` and the replay all stop on it. A result screen already up while a dialog is open over it ignores the pedal and keys (`paused`); the mouse still works. **A new dialog must be added to that list**; `no-scan-behind-dialog.test.js` fails otherwise.
- **One scan at a time** (code review M1): a scan is busy from its first moment (`scanBusyRef`) until its result is on screen; `doTriggerScan` refuses while a result is up or a read is running, and SCAN is greyed while a result is up. Retry on the result screen is how a new read is asked for.
- **The pedal never passes a flagged jersey** (code review H3, agreed with Noam, 23 Nov 2026). A flagged row is open to the matcher from its first flag (see "Coming back at the station"): on an order that was not parked it is offered only as a tap (`tapOnly`, `holdBack` in `src/lib/scanpolicy.js`, tested in `came-back.test.js`), never green by itself, never the first highlight. The ALREADY DONE screen's flagged branch ("Skip" first and highlighted; "🔧 Back from repair — pass it" a mouse click or tap only, `mouseOnly` in `src/lib/dupoptions.js`) is no longer reached by a scan and is kept as a safety net. A passed jersey scanned again offers Skip, Retry, 🚩 Duplicate.
- **The pedal never finishes or starts an order.** Finish order is a click: Enter is swallowed on its confirm, Esc keeps going (code review, 23 Nov 2026). No key acts on the done screen.
- **Retry on a green** (5 Nov 2026: a retry there looked exactly like a confirm and a jersey went in the box unchecked): the retry pedal only lays "That's the retry pedal — Enter confirms" over the screen for 5 s and the green stays; the Retry button on a green is a mouse click only (`mouseOnly`). A real retry (red, yellow, duplicate) keeps an amber "Scanned again · #N is NOT checked — no sticker, no box" strip on the camera screen (`retried`) until the next scan. Floor rule: no sticker, no box.
- Sounds (`src/lib/audio.js`): ascending tone = pass, descending = flag, short beep = scan, two flat blips = retry (nothing recorded).

### Hands-free (`src/lib/motion.js`)

- After a confirm the gate waits for the picture to change and then sit still (~0.8 s); a still picture that is neither the jersey just scanned nor the empty table scans. It works for one jersey placed at a time and for a stack lifted jersey by jersey.

### Unfinished orders (the owner, 19–20 Nov 2026: "store it local to the server", "station agnostic")

"Usually orders ship with others." Boxes stay open until full (45–50 lb), or until the ship-with order or the repairs come; a box is shared by the same team, or the same customer; the count label names both orders with their pieces.

### Saving, pace and attention

- **Saved session** (`src/lib/persist.js`): per station in `localStorage` (`jerseyqc.session.v1.<station>`). Every log entry carries a ~7 KB thumbnail, so 500 scans pass localStorage's ~5 MB by themselves: `sessionBody` drops, in order, the flag photos beyond the newest 20, all flag photos, the thumbnails and model usage figures beyond the newest 60 entries, then all thumbnails; the roster and each entry's match, status, reason and time are always kept. `saveSession` returns false when the write still fails and the header shows a red "NOT SAVING" pill (`saveOk`).
- **Rate and ETA** (`src/lib/pace.js`): from working time, not the clock. The gap between scans counts in full up to 10 minutes (`CAP_MIN`); a longer gap counts as 10, and so does the gap from the last scan to now. The board's rate is the hub's own rolling 20-minute window.
- **Where the screen was** (`src/lib/attention.js`): while an order is open the station records away spells (the page hidden, or another window in front, for 5 s or more: `awaySpells`, `createAwayWatch`) and idle spells (screen up, untouched 3 min+: `idleSpells`, IdleWatch). A page can only see that its own window was left. The spells carry no operator name (owner's decision, 9 Nov 2026), only the station and the times. They go in the session, the hub snapshot (`idle`, `away`) and Excel (see "Reports").

### The ledger

- One entry per scan, filed under the scan's OWN day (from its stamp), keyed `run|id` (or `station|order|id` for events from before runs) (`eventKey` / `fileEvent`; code review M5, 23 Nov 2026). A re-send from any station lands on the same entry; the station that filed it first is kept; a photo once seen is kept. A flag's `garment` and `spots` are kept the same way (`withMarks`): the newest spots that are not empty win, with the garment they were marked on, and a re-send without them never wipes them (the station sends none while the flag is still `locating`). `merge-hub-data.mjs` keeps them too. `normaliseLedger` puts old data right once at hub start and changes nothing on a second run.
- One order record per station, order and run (`station|order|run`) under the day the hub saw it, with the latest roster and statuses, counts, `finishedAt`, idle and away spells. The same run under another number is a rename. A check-off line carries `ledgerId` (`co-<row>-<at>`), so the station's re-send is the same entry. For an order new on a station, the day tally adds only passes the hub has not seen.
- An order is done (`orderDone` in `src/lib/ledgerview.js`) when it has `finishedAt` or nothing left to scan. The board's order view takes the run and day being viewed (`pickRun`: the newest run when none is given) and every event of that run wherever it was scanned (`ofRun`, `eventsAsLog`).
- **90 days** of ledger (`pruneLedger`); photos only on the newest 14 days (`photosPruned: true` on the event afterwards). Open boxes and closed or file-less unfinished entries also go after 90 days.
- Sign out keeps the station on the board, marked; the supervisor's Remove deletes it.

### The data file is never lost (code review M19–M20, 23 Nov 2026)

- Written to `<file>.tmp` and renamed (whole or not at all), at most every 1.5 s.
- A read that fails is tried three more times, half a second apart (OneDrive can hold the file). A file that still cannot be read is NOT set aside and NOT written over: the hub is `blocked`, and every request, reads too, gets a 503 that the stations and the board show, until the server is restarted with a file it can read.
- A file that reads but does not parse is set aside as `.unreadable-…` and the hub starts fresh; if it cannot be set aside, the hub is blocked too.
- **One hub per data file:** the hubs are kept in a map on `globalThis.__jerseyQcHubs`, by file. A new hub on the same file (Vite loading the hub again after a saved server file) closes the old one first: its pending write goes to disk, then the new hub reads the file. From then on the old hub reads each request's whole body and hands it to the newest hub, so a request mid-upload during a reload, or one reaching the old server when the new one failed to start, lands in the new hub. One exit listener flushes every hub; `buildEnd` closes the hub when the server closes.
- Several copies of the data file are merged into one with `node tools/merge-hub-data.mjs --out data/hub.json old1.json old2.json …` (later files win; a photo is kept from any copy; unfinished orders and open boxes are merged by id, the newest change winning; `<name>-orders\` is copied when the output is in another folder).

Two on-screen keys may never be the same: the server checks a floor default with the app's own keys filled in (`KEY_DEFAULTS` in `src/lib/keydefaults.js`, which config.js builds `DEFAULT_SETTINGS` from), and a station drops a floor key that clashes with its effective keys, keeping the operator's (`effectiveSettings`). `PUT /settings/defaults` (change log with before and after; 403 on a read-only production).

## Labels and printers

**The printer.** Labels go to a Zebra ZD411 (203 dpi, ZPL). The station posts the label data to the hub (`POST /api/hub/print`); the hub builds the ZPL (`src/lib/labels.js`, which also runs on the hub, so it never imports config.js: the station passes the tag in) and sends it raw to a Windows queue on the server's PC (`tools/print-raw.ps1`, no driver rendering). Two rolls: the sticker roll (1 × 0.5 in) and the ticket roll: 2 × 1 in, or a tall 2 × 3 in or 2 × 4 in roll, which replaces the 2 × 1 in roll on the ticket printer and takes all its labels (the owner, 23 Nov 2026). A station's ticket roll is `JERSEY_FLAG_LABEL_SIZE_<STATION>`, else `JERSEY_FLAG_LABEL_SIZE` (`flagSpecOf` in hub-plugin.js), so the stations can switch one at a time. The hub knows the roll and builds every label for it: the station sends the same label data whatever the roll.

- **Which queue:** a queue chosen in the admin panel's Printers section comes first (the station's own, then every station's; phase 3, 26 Nov 2026); then a station's own (`JERSEY_PRINTER_<STATION>`, never overridden), else `JERSEY_PRINTER`, else the first Zebra queue on the server PC. A Zebra plugged into the PC the server runs on beats a `JERSEY_PRINTER` / `JERSEY_FLAG_PRINTER` that names a printer shared from ANOTHER PC (the owner, 20 Nov 2026: "make it answer to the servers, not the PCs"; `hubPrinter`). A local name, or a share of the server's own PC, is used as written. The ticket roll's labels go to `JERSEY_FLAG_PRINTER_<STATION>`, else `JERSEY_FLAG_PRINTER`, else the station's sticker printer (`ticketPrinter`). Every copy of `.env.local` still names `\\AK-NB-164\Zebra`.
- The queue list is kept for a minute. A print script still waiting after 30 s is stopped and the station shows, in plain words, which printer did not answer and which PC shares it (`ps1Problem`); PowerShell's own text stays in the server log.
- Development and testing print only with `JQC_STAGE_PRINT=1`; a replay never prints (`holdPrints`).
- **Troubleshooting** (details in `docs/DEPLOY.md`): `tools/printer-check.ps1`, run ON THE SERVER PC, checks a shared printer in four timed steps (name, ports 445 and 135, opening the printer, one test label); step 1 gives the address the server PC is using (12 Nov 2026: the sharing PC moved from wire to Wi-Fi and every label took ~28 s; the cure was on the network side). A shared printer needs the sharing PC on, awake and on the domain network (its firewall lets printer sharing in on the Domain profile only). With the Zebra unplugged, labels wait in the Windows queue and all print when it comes back; `clear-prints.bat` (`tools/clear-print-queue.ps1`), run on the PC the Zebra plugs into, throws them away ("Cleared: N / Left: 0").

**The layouts** (`labels.js`):

- Every label starts 2 mm below the top edge (`LABEL_TOP_MM`, `top` in `labelSize`): the ZD411 cut the first line in half otherwise. On the 2 in wide ticket roll (2 × 1, 2 × 3, 2 × 4 in) text starts 2 mm in from the left (`BIN_LIST_LEFT_MM`): the ZD411 cuts that much.
- No label can wrap over itself: every one-line `^FB` field is squeezed (narrower letters) until its text fits (`line`), with the width estimated letter by letter (`textUnits`: capitals are wide); a list line is one field with no `^FB` box (`tight`), and a long name is squeezed to 70% width before it is made smaller (10 Nov 2026: "11-MACDONALD-AXL" came out as "XL-MACDONALD-A").
- **Sticker** (1 × 0.5 in, kind `jersey`; `jerseyLabel` / `jerseyLabelZPL`): BOX and the number in a left column, TEAM or SIZE and its value on the right, the order number small under it. An order with one box still says the team or the size.
- **Flag ticket** (2 × 1 in, kind `flag`; `flagLabel` / `flagLabelZPL`; owner, 17 Nov 2026): the JERSEY on the left, the DAMAGE on the right. A solid black column (40% of the width) carries the jersey in white: the number as big as it fits, the name, and team · size (one line when it fits, else team over size); no FLAG word, the black says it. The right side is the REASON as big as it fits on up to three lines, the station small, and the order number big at the bottom (`Ord 264247`, ~5 mm; no time or date). No route word and no box. Two copies a flag (`FLAG_COPIES`, `^PQ2`); a reprint from the Print menu is one. The black runs off the top and left edges; the ticket starts 4 dots higher (`FLAG_LIFT`, `^LT-4`) with the texts laid out 4 dots lower. Not more than 4: the printer prints a window one label long, so each dot of lift is a dot lost at the bottom (6 left a white line). The printer keeps `^LT`, so every other label sets `^LT0`. The layout is in fractions of the label, so it also prints on the sticker roll.
- **Tall flag ticket** (a roll 2.5 in tall or more and at least 2 in wide, `isTallTicket`: 2 × 3 and 2 × 4 in): the ticket above, unchanged, in the top inch (`band`; the black column stops there), a thin rule, and under it the garment (`flagLabel` carries `garment` and `spots`; see "Garments") from the FRONT (caption "FRONT · Hockey jersey") and the BACK, each scaled to its half of the room left, 2 mm clear of the left, right and bottom edges (`flagPanels`). The garment goes as ONE picture a side (`^GFA` with Zebra's ASCII compression, `bitmapZPL` / `garmentBitmap`), drawn by the hub on the printer's own dot grid from the drawing's points with a round pen, 3 dots for the outline and 2 for the details: the `^GB` / `^GD` segments it was before printed curves as stairs (the owner's test ticket, 26 Nov 2026). With no spots (Skip, or a reason that does not ask) the garment still prints, empty, and the BACK caption says "Not marked": every tall ticket looks the same. ## Tests and simulations

- **Before every commit:** `npx eslint src hub-plugin.js admin-plugin.js` and `npx vitest run` in the development folder (`npm test` is the same run).
- `vitest.config.js` is the tests' own configuration: automatic JSX, no server plugins (the hub plugin is not loaded), and `.claude/**` skipped (copies of the project there are not this project's tests). Tests run in Node unless the file starts with `// @vitest-environment jsdom`.
- Library tests in `src/lib/__tests__/`. Some hold rules that must not regress: `review-rules` (N1, N2, N4, N5, the no-name rule), `invariants` (a doubtful read is never green, the team column never changes the result…), `typed-number`, `dupoptions`, `no-scan-behind-dialog` (reads App.jsx: the one dialog list, one scan at a time), `review-hub` (the data file), `review-lifecycle`, `review-reports`.
- **Damage location tests:** `garments` (the 13 kinds: a closed outline for each side inside 0–1, details and areas on the garment, `insideGarment`, `spotWords`, `garmentOf` and every catalogue code, `rosterGarment`, the screen's tap maths); `labels-tall` (the tall ticket: every element on the label and 2 mm off the left, the black column stops at the band, spots as `^GC`, stacked or side by side; the box label turned on a tall roll, a lone count label at the top; `repageLists` (the count label and the first rows on one label); `listChunks`); `damage-location-hub` (per-station roll, `POST /print`'s count, spots in the report, kept across re-sends, `normaliseLedger`, `merge-hub-data`, the Where and Garment columns). **`fixtures/labels-2x1.json`** is the output of labels.js before the tall rolls: every 2 × 1 in and sticker-roll label must stay byte for byte the same. A failure there means a label the floor prints today has changed.
- **App smoke tests** (`src/__tests__/app-smoke.test.jsx`, jsdom and Testing Library): the whole station with stand-ins only for the model's read, the sounds, the canvas and the hub. Resume an order; scan → green → checklist → Confirm; Finish of a ship-with order leaves Box 1.1 open on the hub, and New order sends its last report. "Where is the damage": Holes → two spots → Done prints one ticket with the spots; Skip, Esc and the pedal skip; Undo, the 3-spot limit, the double tap; Others, No size tag, Duplicate and Not on the roster never ask it, nor does a sorter's flag; a resumed order on the step prints its ticket once.
- **Operator simulation:** `SIM_ORDERS=3000 npx vitest run operator-sim` works thousands of whole orders through the real libraries and `scanpolicy.js` (roster files with Excel quirks, a camera that hides and misreads digits, an operator who picks, types, flags, un-checks) and fails on a wrong green, a wrong "already passed", an unfinishable order, a lost session, a lost roster row or a broken export. `SIM_TRACE=<order>` prints one order step by step; `SIM_SEED` changes the draw; `SIM_VIGIL=0` turns the self-check off to compare. After any matching change it must show WRONG GREEN 0.
- **Box simulation:** `SIM_BINS=3000 SIM_FACTORIES=30 npx vitest run box-sim` runs the box model against factories whose real numbers are up to 30% off its estimates, with packing noise and wrong taps, and prints the share of right boxes for the flat count (`src/lib/boxes.js`, only the baseline now), the size-and-weight table, the table with learning, and the best any rule could do.
- **Recognition stress test** (live model, ~770 calls, ~4 min): `powershell -File tools/synth-jerseys.ps1` draws 103 synthetic jerseys into `public/sim/stress/synth`; `node tools/stress-distort.mjs <dir with node_modules/sharp>` makes 270 distorted variants of real and synthetic frames; `SHARP_DIR=<same dir> node tools/recog-stress.mjs [runs=2] [filter] [config json]` runs everything through the current prompt, model and matcher and prints a table by category plus every failure with the raw read. Findings are in `tools/RECOGNITION-FINDINGS.md`; add a line there whenever a failure teaches something. `tools/edge-sim.mjs` compares the current code with the demo-day code on real frames.
- **Browser harness:** `tools/browser-harness.js` (paste into DevTools on a signed-in station: a fake camera, a controllable network, a self-driving run) and `tools/break-it.js` (needs the harness). Their by-hand checks still expect the "ENTERED BY HAND" screen, which no longer exists: they need updating.
- **Hub stress:** `node tools/hub-stress.mjs https://localhost:5174 30` hits a RUNNING hub: three stations at 20x the real rate plus a polling supervisor, then every board action (send roster, set number, carried flags, remove, oversize body). The address is required; it refuses 5173 without `--production-yes-i-mean-it`. Restore the data file from a copy afterwards to keep the day sheet clean.

### Replay of a real order (development and testing only)

The ledger keeps the text of every read ("#93? BOZZ [not flat]") and the row the operator ended on, which is enough to run an order again through today's matcher and screens without pictures (`src/lib/replay.js`; on only with `VITE_REPLAY=1`: the floor runs Vite in dev mode too, so `import.meta.env.DEV` is not enough).

- **From the order screen** (the owner, 20 Nov 2026): "▶ Replay an order" (`ReplayFinder`) finds runs by order number (`GET /api/replay?q=`, `replay-plugin.js`): every run of that order in the floor's data file, read only (`C:\JerseyQC\data\hub.json`, or `JQC_REPLAY_FROM`), then in the server's own; a run with no scans is left out; each comes with its roster (statuses off) and its scan events from every day it ran (no photos). Tapping one starts that order and loads the replay bar (`startReplay`; kept in sessionStorage `jerseyqc.replayRun`; ✕ ends it).
- **From a file:** write `{ rows, events }` of the order (from `GET /api/hub/ledger?date=`) to `public/sim/replay-<order>.json` (not in git: a customer's order), send the rows to the test hub as a roster, open `…/?station=station1&replay=<order>` (kept in sessionStorage across the sign-in reload), start that order, press ▶ Play.
- Each read is handed to `doRunScan` in place of the camera (`replayReadRef`, checked first in `readOne`, so the self-check reads it too) with a drawn stand-in frame. After the pause the replay acts as the operator did (confirms the green, picks the same row, "Not on the roster" for an extra, types what was on no list); marks from the table (missing, un-check) are replayed too; a flag on a jersey that had passed is skipped. The panel counts the first screen of every scan: green, lists (and rows per list), red, duplicate.
- While a replay is loaded nothing prints (`holdPrints`: "Replay: nothing is printed"), held at once because the set-out screen prints in its own first effect.
